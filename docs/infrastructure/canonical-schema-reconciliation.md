# Canonical project — read-only inventory, recovery and reconciliation (ENV-CANON-01)

Project: **fitmatch-ai / `gohczmqykjkrgdblgbog`** (BACKEND-024). It holds real wardrobe/auth/storage data. This document is a procedure and a proposal template; it does not authorize any cloud change. Each step that changes the cloud needs its own reviewed plan and the owner's approval.

**Status at handoff (CL-CANON-20261109-01): NOT RUN.** This session has no authorized access to the canonical database (the connected Supabase account sees another org; no DB credential is to be requested in chat). Everything below is ready to run by the owner from the Dashboard, or by an agent once a correctly scoped read-only connection exists.

## 1. What the repository proves and what it does not

- `docs/infrastructure/schema-manifest.json` is generated by `node scripts/schema-manifest.mjs`: the base `supabase/schema.sql` plus all 12 migrations applied in filename order to a Supabase-like stub in disposable Docker PostgreSQL 16 (no network), with the object set added/changed by each step. `--check` regenerates and fails on drift; it also self-checks that the fully migrated stub reads "applied" for every step.
- It does **not** prove that the cloud database matches. The cloud may have only `schema.sql` (pasted earlier), some migrations, manual edits, other apps' objects (the org also contains `lifedashboard`), or Supabase-version differences.

## 2. Read-only inventory (Dashboard → SQL editor, correct account)

1. Run `scripts/schema-inventory.sql`. It reads system catalogs only: tables/columns/constraints/indexes (public, storage, auth, supabase_migrations), public functions (signature, security definer, md5 of the body, anon/authenticated EXECUTE), policies (md5 of expressions), triggers, SELECT grants, extensions, planner row estimates. No user rows, no object names.
2. Run the bucket query and merge its result into the saved JSON as `"buckets"`:

   ```sql
   select coalesce(jsonb_agg(jsonb_build_object('id', b.id, 'public', b.public,
            'fileSizeLimit', b.file_size_limit, 'allowedMimeTypes', b.allowed_mime_types,
            'objects', (select count(*) from storage.objects o where o.bucket_id = b.id),
            'bytes', (select coalesce(sum((o.metadata->>'size')::bigint), 0) from storage.objects o where o.bucket_id = b.id))
          order by b.id), '[]') as buckets
   from storage.buckets b;
   ```

3. Only if the inventory lists `supabase_migrations.schema_migrations`: `select version, name from supabase_migrations.schema_migrations order by version;` (history of the CLI; absence is normal if SQL was pasted).
4. Save the outputs **privately** (local disk of the owner, not GitHub/Drive public, not chat). They contain schema shape and aggregate counts only, but still describe a production system.
5. Compare offline: `node scripts/compare-schema-inventory.mjs docs/infrastructure/schema-manifest.json <saved.json>`.

Reading the result:

| Status | Meaning | Next |
|---|---|---|
| applied | every object of the step exists with the expected definition (or a later step redefines it) | nothing for this step |
| absent | none of the step's objects exist | candidate for the additive plan, in order |
| partial | some objects missing | **stop**: find out why (manual edit, failed paste) before anything else |
| present-differs | objects exist with another definition | inspect each key; policy/constraint text may differ by server version; never overwrite blindly |
| extra objects | exist in the cloud, not created by the chain | **do not drop**; record owner/purpose; check name conflicts with planned objects |
| RLS disabled / public bucket | security drift | report to owner; fixing it is its own reviewed change |

## 3. Recovery before any change

Do not assume automatic backups: the free plan has no point-in-time recovery, and daily backups depend on the plan. Before the first additive migration:

1. Private logical backup of the database (owner's machine): `supabase db dump` for schema and `supabase db dump --data-only` for data (Supabase CLI, linked to `gohczmqykjkrgdblgbog` with the owner's own login), or `pg_dump` with the connection string from the Dashboard. Store encrypted/private; never commit; never paste the password.
2. Storage: list per bucket counts/bytes (query above) and copy `fitmatch-wardrobe` / `fitmatch-v2` objects privately if the plan touches storage policies or buckets.
3. Prove the backup restores: load the dump into disposable Docker PostgreSQL and run `scripts/schema-inventory.sql` there; the comparison must match the cloud inventory.
4. Rollback plan per change: for the Qwen pilot the emergency rollback is `QWEN_ANALYSIS_ENABLED=0` + ungrant the scoped worker; never drop schema or recreate the project.

## 4. Reconciliation proposal template (fill after step 2)

- Inventory date, Dashboard account used, compare output summary (statuses per step).
- Per absent step: migration file + sha256 (from the manifest), objects it adds, conflicts found (none / list), dependency on earlier steps.
- Per partial/present-differs step: exact keys, observed vs expected, cause, decision (adopt cloud definition into a new migration / write a corrective additive migration / owner decision).
- Extra objects: list, owner, keep.
- Staging: the exact SQL to apply, run first on Docker restored from the private dump; DB + HTTP regressions on that restore.
- Approval: Codex review + owner; then apply in one transaction per migration, re-run the inventory and compare (all applied), then and only then enroll the pilot worker.
